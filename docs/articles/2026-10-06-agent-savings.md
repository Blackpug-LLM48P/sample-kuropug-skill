# 今更聞けない、AIエージェント運用の節約術

――dotを使い始めて、仕事の回し方が変わった

「50％高速化」という話を見て、思った。

速さが問題じゃねえんだよ。

もちろん、返事が早いのはうれしい。待っている間にコーヒーを淹れたら、もう終わっている。それは助かる。ただ、週間リミットにぶつかる使い方をしていると、別の問題が残る。速く処理できても、その週に必要な仕事を全部回せるとは限らない。

429は敵。
でも、今回の話はHTTP 429の対処ではなく、限られた利用枠でどう仕事を回すかです。

## 前からやっていたことが、Claude側にもあった

黒パグスキルには以前から、精度と消費を確認し、同じ情報や成果を再利用し、モデルや推論量を下げるのは最後、という方針を入れていた。

最近、Claude側の公開スキルを探してみたら、Anthropic公式のコスト最適化ガイドにも近い順序があった。キャッシュ、入力、反復処理、出力などを先に改善し、モデルや推論量の変更は後から品質と一緒に評価する。評価の単位も、仕事を一つ完了するまでのコストになっている。[1]

これはAPI料金の話なので、そのままサブスクの週間枠へ換算はできない。それでも、安いモデルで失敗して、やり直して、人間が修正するところまで含めて考える方針は共通している。

自分の運用で、この方針が具体的な仕事の流れになったのは、dotを使い始めてからだった。

## Workで条件を整え、dotへ仕事を渡す

現在は、Workを指示と判断の司令塔にして、dotへ実作業を渡している。

文章鑑識の開発なら、比較する版、使う文章、試行回数、保存するもの、終了条件を決める。実行後は、結果と原出力、検証記録、未解決事項を次の工程へ渡す。毎回、それまでの会話全部を読み直して「で、何をするんでしたっけ」となるのは避けたい。

今回の成果物には、6文章×2版×2反復の24件比較が残っている。その後の工程ではRC草案、つまり公開前の候補を作り、13本の回帰チェックと、既存24件・修正見本9件の規定チェックまで進めた。

ここで大事なのは、数を回したことだけではない。実際に、原文の「紙が足りないことはある」が、説明では「紙は足り得る」へ変わった例が見つかった。引用と計算が正確でも、その説明まで正しいとは限らない。この問題を記録して次へ渡すところまでが仕事になる。

指示書ができた、実行を頼んだ、結果が出た、結果を検証した。この四つも別々に扱う。「準備しました」で実行済みにすると、次の工程は存在しない結果を待つことになる。

dotの費用対効果を自分が感じるのは、こうした反復作業を任せられるところだ。以前は検証の待ち時間に離れにくかった。今は条件を渡して、結果を確認する場面へ戻れる。人間の拘束時間は未計測なので、何時間節約したとは言えないけれど、仕事の回し方は変わった。

任せるための指示と、返ってきた結果を確かめる手間は必要です。「好きにやっといて」で放置するほど、最後の確認が安く済むとは限らない。

## スクショに残った、この数日

統計画面の累計表示を、画面内の日時で並べるとこうなった。時刻は日本時間。

| 日時 | 累計トークン数 |
| --- | ---: |
| 10月3日 8:11 | 45.2億 |
| 10月4日 22:16 | 51.9億 |
| 10月5日 5:28 | 52.8億 |
| 10月6日 7:43 | 59億 |
| 10月6日 13:43 | 60.1億 |

表示上の増加は14.9億。最後の画面では最長タスクが4時間5分、連続利用日数は47日だった。

一方、10月6日の自分の会話記録には、朝の週間残量70％、午前中から検証を回した後で69％という観測がある。土曜朝のリセットを待つ状態で、この残り方には驚いた。

ただ、累計表示と週間残量は別の数字です。14.9億を今週の課金対象トークン数と呼ぶことも、dotだけの消費と呼ぶこともできない。内部の計上方法やアカウント条件を揃えた比較ではないので、dotやスキル単独の改善率も出せない。

ここで示せるのは、作業の成果物が残り、その間の表示も記録できた、という範囲。これから同じ作業の完了数と残量を一緒に追うための出発点になる。

## 節約するなら、この順番で

黒パグ式の運用を、実践用に七つへ整理するとこうなる。

① 精度と、仕事一つあたりの消費を確認する。  
一回の返答が安くても、三回やり直せば話が変わる。検証なら同じ条件で、完了までの試行数と結果を残す。見えない使用量は未計測にしておく。

② 同じ入力と成果を再利用する。  
確認済み資料、共通の指示、前の工程の結果を使う。APIならPrompt Cachingも検討する。これは条件を満たす入力の再利用に関する機能で、資料を保存しただけでキャッシュが成立するわけではない。[2]

③ 必要な情報をツールで取りにいく。  
ファイルがあるなら、まず必要な箇所を探す。本文の一部分で済む問いに、資料一式を毎回投入しない。ただし、全文の照合が必要な検証では読む範囲を削らない。

④ 長い会話は、仕事の引き継ぎへ変える。  
目的、固定条件、決定事項、根拠の場所、未完了事項を残す。原出力は参照先に保持する。短い要約だけを残して証拠を捨てると、あとで確認するために同じ作業をやり直すことになる。

⑤ 出力は次の工程に必要な形で残す。  
24件を比較するなら、長い感想を24本もらうより、対応する原出力と比較表、問題箇所が欲しい。説明を短くすることと、検証できなくすることは別なので、根拠は残す。

⑥ 待たなくてよい反復は、まとめて任せる。  
dotへ連続作業を渡す場合も、途中保存と停止条件を決める。計算や照合はコードに任せられる部分がある。APIのバッチ割引は別の料金制度なので、dotへまとめて渡すだけで同じ割引が付くとは考えない。

⑦ それでも重ければ、モデルや推論量を見直す。  
ここで初めて、同じ評価条件で比較する。下げた結果、失敗と再試行が増えたなら、その仕事には節約になっていない。

返答までの速さ、API料金、週間枠、人間の作業時間。どれを改善したいかで、確かめる数字は変わる。自分は週間枠の残量だけ眺めて「減ってない！」と喜ぶ前に、何が完了したかも並べておきたい。枠だけ残って成果物が空では、犬がサボっただけになる。

## ネタ枠：60.1億をAPI代に換算する

せっかくなので、仮想レシートを出してみます。

2026年10月6日に確認した標準処理・短いコンテキストのAPI料金は、100万トークンあたり、GPT-6.1 Solが通常入力2ドル、キャッシュ済み入力0.10ドル、出力10ドル。GPT-6 Astraは順に10ドル、1ドル、50ドルだった。[3][4]

総数の80％を入力、20％を出力と仮定する。円換算は比較用に1ドル150円。キャッシュありの行は、入力の90％をキャッシュ済みとして計算した。

| 仮定 | 累計60.1億 | 増加14.9億 |
| --- | ---: | ---: |
| Sol・キャッシュなし | 約324.5万円 | 約80.5万円 |
| Sol・入力の90％がキャッシュ | 約201.2万円 | 約49.9万円 |
| Astra・キャッシュなし | 約1,622.7万円 | 約402.3万円 |

レシートが巻物になった。

これは実際の請求額でも、節約額でも、OpenAIの原価でもありません。統計画面の数がAPI課金の対象とどう対応するかは未確認で、モデルや入力・出力・推論の内訳も不明。現在の単価を仮に当てただけです。キャッシュ書き込み、長いコンテキストや高速処理の料金変更、ツール料金、税金も入れていない。

数字の勢いで「サブスクで1,600万円得した！」まで走ると、電卓が仕事をしすぎる。同じ総数でも条件によって金額が変わる、というところでレシートを畳んでおきます。

## 次の仕事で確かめること

- [ ] 完了の条件と、比較する品質を決めたか。
- [ ] 同じ資料や結果を取り直していないか。
- [ ] 引き継ぎから原出力と根拠へ戻れるか。
- [ ] 反復処理の途中保存と停止条件があるか。
- [ ] 指示、実行、検証の状態を区別したか。
- [ ] モデル変更後の失敗や再試行も数えたか。

最初から大きな仕組みを作る必要はない。次の反復作業で、固定条件と保存先を渡してみる。戻ってきた成果物で次へ進めるか、それとも説明し直しになったか。そこから直せる。

黒パグ式の公開サンプルはGitHubに置いてあります。[5] 資料の主張とAIの解釈を分け、出典を残し、具体的な次の仕事へつなぐ最小実装です。今回の七段階を丸ごと収録した配布版ではありませんが、根拠を残して工程をつなぐ形は試せます。

導入するときは、使う環境に合わせて配置方法を確認してください。まず一つの資料で、要約を読んだあと実際に次の作業へ進めるか。お試しはそこからでどうぞ。
